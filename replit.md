# Workspace

## Overview

Auditee is an AI-native enterprise platform designed to manage the entire Product Development Lifecycle (PDLC). It offers comprehensive tools for requirements management, traceability, compliance, defect tracking, and advanced AI-powered analysis and report generation. The platform aims to automate and streamline product development processes, providing a holistic solution for businesses. Key capabilities include AI-driven requirement generation, code analysis, compliance auditing, extraction from legacy systems, and natural language Q&A. The project includes a marketing landing page and a core application, with a focus on delivering a robust, AI-accelerated PDLC management experience.

## System Architecture

The project is built as a pnpm workspace monorepo using Node.js v24 and TypeScript v5.9.

### UI/UX Decisions

The marketing site is optimized for SEO with extensive meta tags, Open Graph, Twitter Cards, and JSON-LD, along with `robots.txt` and `sitemap.xml`. The application (`/app/*`) is configured with `noindex, nofollow`. The application's navigation is structured logically, and a floating "Ask Auditee" button provides quick access to AI chat. The UI adheres to a branded `shadcn` appearance with Auditee purple (`#6366f1`) and Inter Tight font.

### Technical Implementations

The backend is an Express 5 API server mounted at `/api`. Data persistence is handled by PostgreSQL with Drizzle ORM. Zod and `drizzle-zod` are used for validation. API client code is generated from an OpenAPI specification using Orval. Frontend is developed with React and Vite. All external HTTP requests are routed through `lib/safe-fetch.ts` for SSRF protection. The system implements a robust authentication and authorization mechanism using Clerk (white-label) and a workspace-scoped, seat-based billing model.

### Enterprise Features

- **RBAC (4 roles)**: `owner`, `admin`, `editor`, `viewer`. The permission matrix lives in `artifacts/api-server/src/lib/permissions.ts` (`canManageBilling`, `canManageMembers`, `canChangeRoles`, `canManageSso`, `canViewAuditLog`, `canEditContent`, `canViewContent`). Server-side `permissionsFor()` and `isAtLeast()` are the authoritative checks. Legacy `member` rows are normalized to `editor` via `canonicalRole()`. Role changes on owner/admin targets are owner-only and serialized via `FOR UPDATE` locks; the last-owner demotion guard runs inside the same transaction.
- **Audit Log**: append-only `audit_logs` table (workspaceId, actorUserId, actorEmail, action, resourceType, resourceId, metadata jsonb, ip, userAgent, createdAt; indexed on workspaceId+createdAt). Mutations write rows via the best-effort `auditLog()` helper (`artifacts/api-server/src/lib/auditLog.ts`). Read endpoint `GET /api/workspace/audit-logs` requires admin+ role and Enterprise plan; UI at `/app/audit-logs` with filters and CSV export.
- **SSO (SAML / OIDC via Clerk Enterprise)**: `workspaces.sso_enabled` + `workspaces.sso_domain` for domain auto-routing. `POST /api/workspace/sso` is owner-only and Enterprise-only (returns 402 `requiresUpgrade` for Free/Pro). UI at `/app/sso` includes Okta / Entra ID / Google Workspace setup links. Plan downgrades from Enterprise automatically clear `sso_enabled` / `sso_domain`.
- **Plan-gating**: `planAllows(plan, feature)` enforces the Enterprise-only feature set (`audit_log`, `sso`). Endpoints return HTTP 402 with `requiresUpgrade: true` so the frontend can render upgrade CTAs.
- **Per-project RBAC (4 project roles)**: `manager`, `developer`, `reviewer`, `auditor`, layered on top of the workspace roles. Projects are scoped to a workspace via `projects.workspace_id` (NOT NULL FK→workspaces, indexed). The `project_members` table (unique on `projectId+userId`) holds explicit grants. Workspace `owner`/`admin` are auto-`manager` on every project in their workspace. Permissions are computed in `artifacts/api-server/src/lib/projectPermissions.ts` and access is loaded by `artifacts/api-server/src/lib/projectAccess.ts`, which exposes two inline helpers: `requireProjectAccessInline(req, res, projectId, minRole)` — strict (401 anon, 403 forbidden, returns access on success) — used everywhere project data is read or written; and `assertProjectAccessIfAuthed(req, res, projectId, minRole)` — kept only for the AI **anon trial** path on `/ai/ask` (returns `null` for anon, `false` after writing a 403, access on success). The `requireProjectAccess(minRole)` middleware is the route-level form of the strict helper. Standard matrix: Manager=full incl. member management; Developer=read+write content (requirements/sources/reports); Reviewer=read+comment/approve, no content edits; Auditor=read-only. Write & read enforcement is applied across `routes/requirements.ts`, `routes/sources.ts` (incl. source-file content reads), `routes/reports.ts` (incl. `/reports/:id/export`), `routes/comments.ts`, and the project-scoped paths in `routes/ai.ts` (`/ai/ask`, `/ai/ask/history`, `/ai/gap-analysis`, `/ai/gap-analysis/promote`, plus the existing generate/audit endpoints). All listing endpoints require an explicit `projectId` query param so the access check has something to authorize against — this prevents cross-workspace enumeration. `reconcilePendingInvites` (in `lib/authContext.ts`) attaches both pending workspace invites **and** pending `project_members` rows to a Clerk userId on first sign-in, matching by lower-cased email. `GET /api/projects/:id` and the project list both include an `effectiveRole` field for the calling user; the frontend exposes it via `useProjectContext()` (`effectiveRole`, `canEditContent`, `canManageMembers`) and surfaces a role badge near the project picker. Project member CRUD lives at `GET/POST/PATCH/DELETE /api/projects/:id/members` and is exposed in the UI at `/app/members` (`pages/app/ProjectMembers.tsx`). All member changes write `audit_logs` rows. Out-of-scope routers not yet migrated to the strict helper: `routes/code-artifacts.ts`, `routes/traceability.ts`, `routes/capa.ts`, `routes/defects.ts`, `routes/workflows.ts` — these still gate writes via `requireSession` only and do not enforce per-project role.
- **Trust / Security center**: public `/security` page documents encryption (TLS 1.3, AES-256), SSO + RBAC + audit log capability, SOC 2 / ISO 27001 / GDPR / HIPAA posture (precise wording — "aligned with"/"designed for"/"ready for", never false "certified" claims), sub-processors list, and security@auditee.com vulnerability disclosure. Linked from the marketing nav (Resources) and footer.

AI features are accessible via `/api/ai/*` endpoints and include functionalities like `generate-requirements`, `analyze-code`, `compliance-audit`, `legacy-extract`, `ask`, `gap-analysis`, `promote`, and `estimate-effort`. AI document generators support various report types (e.g., `compliance_audit`, `requirements_summary`) and can export to DOCX/PDF/HTML, leveraging canonical blueprints. Standards-aware generation is a core feature, allowing AI outputs to conform to multiple regulatory frameworks (e.g., HIPAA, IEC 62304, SOC 2) through dynamic blueprint application. The system supports free-trial AI credits with a mechanism for anonymous and Free plan users, including atomic credit consumption and refund on failure.

### Standards Documentation Set

The AI report engine ships canonical IEEE/ISO blueprints for the full software-engineering documentation chain. `artifacts/api-server/src/routes/reports.ts` defines `KIND_BLUEPRINT` entries for `architecture_doc` (ISO/IEC/IEEE 42010 — Context, Stakeholders & Concerns, Viewpoints, Views, Architecture Decisions, Cross-Cutting Concerns), `hld` and `lld` (IEEE 1016 — module decomposition, component diagrams, data-flow, integration points; class/function specs, API contracts, sequence narratives, data structures, algorithms), `deployment_doc` (Environments, Topology, CI/CD, Rollout, Rollback, Runbook), and `user_manual` (IEEE 1063 — Audience, Concepts, Task Procedures, Reference, Troubleshooting, Glossary). Each blueprint provides per-section word budgets and "must cover" prompts that are concatenated with the user-selected standards (e.g. HIPAA, IEC 62304) into the AI generator. All five kinds export to DOCX/PDF/HTML through the existing report pipeline. Friendly labels live in `KIND_LABELS` / `KIND_DESCRIPTIONS` in `artifacts/eltegra-site/src/pages/app/Reports.tsx`.

### 5-Stage Lifecycle Traceability

Traceability is computed end-to-end across **Architecture → Design → Implementation → Testing → Deployment**. The deterministic graph is served by `GET /api/traceability/lifecycle?projectId=` (in `artifacts/api-server/src/routes/traceability.ts`); each requirement carries a `n/5` completeness badge plus per-stage status. The `/api/ai/traceability-audit` endpoint scores the same five stages and returns per-stage recommendations. Heuristics: Architecture stage is satisfied when a requirement links to an `architecture_doc`/`hld` report **or** has a `kind=architecture` traceability link; Deployment stage is satisfied by a `deployment_doc` report, a `kind=deployment` link, or detected files matching `Dockerfile`, `k8s/**`, `.github/workflows/**`, or `terraform/**`. Frontend `Traceability.tsx` renders the five-column `LifecyclePanel`; the data hook is `useLifecycleTraceability` in `artifacts/eltegra-site/src/lib/ai-api.ts`.

### Automated Control Closure & Evidence Locker

Compliance controls auto-close as new evidence arrives. When `/api/ai/gap-analysis/promote` creates a requirement that maps to one or more controls, those mappings are written and each control's `assertion` column flips to `Met (AI-asserted)`; an `ai_asserted` row is inserted into the new `compliance_evidence` table (`lib/db/src/schema/complianceEvidence.ts`) recording the source requirement, file path, or report. `POST /api/compliance/controls/:id/verify` lets an editor+ flip the assertion to `Met (Verified)` or `Rejected`, both transitions appended to `complianceEvidence` and the `activity_log` (shared `artifacts/api-server/src/lib/activityLog.ts` helper). `GET /api/compliance/controls/:id/evidence` returns the full evidence trail. `compliance_audit` runs are no longer purely advisory: any control the audit confirms as Met now writes a corresponding evidence row. UI lives in `artifacts/eltegra-site/src/pages/app/ComplianceDetail.tsx` (per-control `Met-Verified | Met-AI | Open | At-Risk` badge, expandable evidence list, Verify/Reject buttons via `lib/compliance-api.ts`).

### Test Management & Notifications

A first-class test-cases module backs the standalone `/app/tests` page. Schema: `lib/db/src/schema/testCases.ts` (`id`, `projectId`, `requirementId`, `title`, `type` ∈ functional/negative/non_functional/acceptance, `steps[]`, `expected`, `status` ∈ draft/passing/failing/blocked, `priority`, `tags`, `lastRunAt`, `lastRunNote`). REST surface: `GET/POST /api/test-cases`, `PATCH/DELETE /api/test-cases/:id`, `POST /api/test-cases/:id/run`, and `POST /api/test-cases/bulk-by-requirement` for per-requirement summaries (in `artifacts/api-server/src/routes/testCases.ts`). AI suite generation is `POST /api/ai/generate-test-cases` body `{requirementId}` — produces a typed suite, persists it, tags rows `ai-generated`. The frontend page (`artifacts/eltegra-site/src/pages/app/TestCases.tsx`) provides status/type/requirement filters, summary KPIs, edit/delete dialogs, and one-click run-status toggles. The Requirements detail sheet renders an inline `RequirementTestCasesPanel` with a per-requirement "Generate" button. **Stale-requirement notifications**: the existing recurring-audit scheduler (`artifacts/api-server/src/lib/scheduler.ts`) now also calls `runStaleRequirementsDigest()`. For every project, it finds requirements that have been `documented` for >7 days with **no** test cases and **no** code-or-test traceability links, then emits one `stale_requirements_digest` in-app notification per project member. The check is idempotent (skipped if a digest was emitted in the last 24 h) and surfaces in the existing notification bell at `link: /app/requirements`.
